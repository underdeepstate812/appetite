# @apetite/admin

React + Vite + TypeScript. Панель бизнеса — ШАГ 10. Панель платформы (модерация,
GMV, комиссия по всем заведениям) — ШАГ 11. Одно приложение, два раздела —
после входа роль аккаунта (`BUSINESS`/`ADMIN`) определяет, какой из них виден.

## Стек

- **React 19 + Vite 6** — без CRA/Next, простая SPA, `react-router-dom` (v6) для
  Login/Offers/Orders/Analytics.
- **Zustand** — тот же паттерн стора, что и в mobile (`authStore.ts` почти дословно
  повторяет `apps/mobile/src/store/authStore.ts`, только localStorage вместо
  secure-store — веб-only, платформенного разделения не нужно).
- **Без UI-библиотеки** — простая собственная CSS-система (`styles/global.css`) с
  токенами, повторяющими палитру мобильного приложения (`primary`/`success`/
  `warning`/`danger` + soft-tint варианты) для визуальной согласованности бренда.
  Только светлая тема — это рабочий инструмент для персонала, не потребительское
  приложение; тёмный режим сюда осознанно не добавлен (упрощение скоупа ШАГ 10).
- **Без i18n** — только RU. Единственная аудитория — русскоязычные владельцы
  заведений в пилоте (Москва, ШАГ 0), английский для admin не нужен.

## Структура

```
src/
  api/          — тот же fetch-клиент паттерн, что в mobile (JWT + авто-refresh);
                  platform.ts — отдельный клиент для /platform/* (ADMIN-only)
  store/        — authStore (BUSINESS и ADMIN), businessStore (моё заведение —
                  только для BUSINESS, ADMIN на него не претендует)
  components/   — Layout (сайдбар меняется по роли), Modal, OfferFormModal,
                  OnboardBusinessModal, StatusBadge (+ BusinessStatusBadge),
                  StatCard, StateViews
  pages/        — LoginPage, OffersPage, OrdersPage, AnalyticsPage (BUSINESS),
                  PlatformBusinessesPage, PlatformStatsPage (ADMIN)
  styles/       — global.css (токены темы + примитивы: card/btn/badge/table/field)
  constants.ts  — CATEGORY_LABELS (общий для офферов и онбординга заведений)
```

Роль определяет и стартовый редирект после входа, и доступные маршруты:
`RequireRole` в `App.tsx` отправляет BUSINESS/ADMIN обратно на "свою" домашнюю
страницу при прямом заходе на чужой URL — совпадает с тем, что бэкенд и так
вернёт 403 на чужие эндпоинты (`RolesGuard` без автоматического ADMIN-бэкдора,
роль проверяется строго по списку в `@Roles(...)`), так что фронтенд просто не
даёт увидеть пустой экран с ошибкой вместо реального UI.

## Функциональность (ШАГ 10)

- **Вход**: только для роли `BUSINESS` — `POST /auth/login`, если у аккаунта другая
  роль (`USER`/`ADMIN`), сразу показывается понятная ошибка, а не пускает в пустую
  панель.
- **Офферы**: таблица офферов заведения (`GET /offers?businessId=`), создание
  (`POST /offers`), редактирование (`PATCH /offers/:id`) — с explicit-полем "текущая
  скидка X% — пересчитывается автоматически", т.к. `discountPercent`/
  `discountedPrice` не редактируются вручную (это работа шедулера из ШАГ 5). Архив
  (мягкое `status: ARCHIVED`) — первый шаг; жёсткое удаление доступно только из
  архива, чтобы нельзя было случайно удалить активный оффер с проданными
  экземплярами.
- **Заказы**: список заказов заведения (`GET /orders`, бэкенд уже сам скоупит по
  роли — без параметров), подтверждение выдачи прямо в строке таблицы — ввод
  6-значного `pickupCode`, который называет покупатель, → `PATCH /orders/:id/complete`.
  Неверный код показывает ошибку инлайн, не блокируя остальную таблицу.
- **Аналитика**: сводка по заведению — активные офферы, выручка и комиссия
  платформы (только по `COMPLETED`-заказам), спасённые кг, разбивка заказов по
  статусам. Новый backend-эндпоинт `GET /businesses/:id/stats` (см. корневой
  README) — **кросс-заведенческий GMV платформы сюда не входит, это отдельная
  платформенная сводка ШАГ 11**.

## Функциональность (ШАГ 11) — панель платформы, роль ADMIN

- **Вход**: тот же `POST /auth/login`, теперь пускает и `ADMIN` — после входа
  сразу видно раздел платформы (Заведения/GMV), а не пустую страницу с
  BUSINESS-навигацией.
- **Заведения (модерация + комиссия)**: таблица ВСЕХ заведений платформы
  (новый `GET /platform/businesses` — совмещает данные заведения со сводкой
  заказов, чтобы не гонять два запроса на один список), с колонками статуса,
  комиссии, выданных заказов и выручки. Комиссия редактируется инлайн в
  таблице (`PATCH /businesses/:id { commissionPercent }` — новое поле DTO,
  backend молча игнорирует его для не-ADMIN, как и `status` до этого).
  Блокировка/разблокировка — тот же `PATCH .../status`, что уже был ADMIN-only
  с ШАГ 4, просто наконец получил UI. Кнопка «Онбординг заведения» — форма на
  уже существующий `POST /businesses` (создаёт и владельца, и заведение одним
  запросом, ШАГ 0/4) — тоже раньше был без UI, только curl/Postman.
- **GMV**: платформенная сводка — новый `GET /platform/stats`. GMV и доход
  платформы считаются по `COMPLETED`-заказам ВСЕХ заведений сразу (в отличие
  от per-business `/businesses/:id/stats` из ШАГ 10), плюс разбивка заведений
  по статусу и заказов по статусу.

## Быстрый старт

```bash
cp .env.example .env   # VITE_API_BASE_URL
pnpm dev:admin          # http://localhost:5173
```

Backend должен быть поднят (`docker compose up -d` или `pnpm dev:backend`).
Демо-вход: `cafe.pushkin@apetite.ru` / `password123` (бизнес, или любое из
четырёх сид-заведений — см. корневой README) либо `admin@apetite.ru` /
`password123` (платформа).

## Docker

`docker-compose.yml` теперь собирает admin как реальный multi-stage билд (было —
nginx-плейсхолдер с одним `index.html` до ШАГ 10): `context: .` (корень монорепо,
как у backend) — нужен доступ к `@apetite/shared`; `pnpm run build` → статика в
`nginx:alpine` с SPA-фолбэком на `index.html` (`nginx.conf`), чтобы прямой заход на
`/offers` не давал 404. `VITE_API_BASE_URL` передаётся как build `ARG`, не рантайм
`ENV` — Vite инлайнит переменные в бандл на этапе сборки (как Expo с
`EXPO_PUBLIC_`), рантайм-переменная контейнера на уже собранный статический бандл
повлиять не может.

## Известные упрощения

- Одно заведение на аккаунт (ШАГ 0) — `businessStore` берёт первый элемент из
  `GET /businesses/mine`, без UI-переключателя между несколькими заведениями.
- Подтверждение выдачи — только ручной ввод pickup-кода. QR-сканирование камерой
  (upd. коммент в `orders.service.ts` про "Admin-панель сможет сканировать") — не
  реализовано в бете, ручной ввод полностью покрывает сценарий и проще для kiosk-режима
  на любом устройстве без камеры.
- Нет пагинации у `GET /orders`/`GET /offers?businessId=` сверх стандартной
  `pageSize` офферов — для беты с несколькими заведениями и умеренным объёмом
  заказов достаточно, backend-пагинация заказов — по необходимости в ШАГ 13+.
- `window.confirm()` используется напрямую (не `Alert`-обёртка, как в mobile) —
  это чистый web-контекст, нативный диалог браузера работает без дополнительных
  обёрток.

## Проверено вживую

Полный цикл в браузере против реального backend: вход владельцем «Кафе Пушкинъ» →
список офферов → создание нового оффера (форма, валидация, дефолтные даты
самовывоза) → редактирование (discount-инфо read-only) → архивация → удаление из
архива → список заказов → подтверждение выдачи неверным кодом (ошибка инлайн) →
верным кодом (статус обновился без перезагрузки) → аналитика (выручка/комиссия/кг
совпадают с ручным расчётом по данным backend) → выход → попытка входа под
`USER`-аккаунтом отклонена с понятным сообщением. Найденный и исправленный по
пути баг вёрстки: таблицы офферов/заказов использовали `overflow: hidden` на
карточке-обёртке вместо `overflow-x: auto`, из-за чего крайняя колонка с кнопками
действий обрезалась и была недоступна — заметно уже на первом скриншоте.

Один пункт не проверен до конца: клик "да" в диалоге `confirm()` при архивации/
удалении/блокировке — built-in browser tool этого окружения намеренно подавляет
нативные диалоги (та же особенность, что и в mobile-тестах ШАГ 8/9); сам
PATCH/DELETE-запрос проверен напрямую `curl`'ом с реальными токенами и
подтверждён визуально после релоада.

### ШАГ 11 — проверено вживую

Вход `admin@apetite.ru` → сразу раздел платформы (не пустая BUSINESS-навигация)
→ таблица всех 4 сид-заведений с верной выручкой/заказами → инлайн-редактирование
комиссии (20% сохранилось, проверено рефетчем) → блокировка/разблокировка (через
`curl`, UI подтверждён визуально после релоада — тот же confirm()-лимит, что
выше) → онбординг нового заведения через форму (появилось в списке с дефолтной
комиссией 25%) → GMV-страница: цифры (450 ₽ GMV, 113 ₽ доход платформы, 0.6 кг,
5/5/0/0 заведений, 2/1/1/0/0 заказов) совпадают и с ручным расчётом, и с тем, что
показывает BUSINESS-панель «Кафе Пушкинъ» для того же единственного заказа с
реальной выручкой — кросс-проверка, что platform-агрегация и per-business
агрегация не разошлись. Разделение ролей проверено в обе стороны: ADMIN не
видит BUSINESS-навигацию и наоборот, прямой заход BUSINESS-аккаунта на
`/platform/businesses` молча редиректит обратно на `/offers` (та же логика,
что и 403 от бэкенда, только без страницы ошибки).
