# Бэклог после беты (ШАГ 14)

Бета (ШАГ 0–13) закрыта: mobile-приложение, backend, панель бизнеса и панель
платформы работают вместе, живьём проверены, 53/53 smoke-тестов проходят.
Этот документ — не новый функционал, а инвентаризация всего, что было
сознательно упрощено или отложено по пути, собранная в одном месте, чтобы
решения ШАГ 0 не растворились в истории коммитов. Порядок разделов — по
убыванию того, что стоит сделать перед реальным (не пилотным) запуском.

## Перед показом реальным пользователям (не бета-демо)

Это не "было бы неплохо" — без этого реальный пилот либо не заработает, либо
будет ломать доверие пользователей.

- **Реальный платёжный провайдер.** `PaymentProvider` — интерфейс, mock-реализация
  синхронно "успешна" всегда; `POST /payments/webhook` существует только как
  контракт для будущего провайдера ([README.md](../README.md), секция ШАГ 5).
  Подключение — новый класс за тем же интерфейсом, DI-биндинг, без изменений в
  `OrdersService`.
- **Реальная доставка push.** Регистрация токена работает и не падает на
  web/без EAS `projectId`, но сама доставка через Expo Push API не проверена
  ни разу — `EXPO_PUSH_MODE=mock` везде ([apps/mobile/README.md](../apps/mobile/README.md)).
  Нужен EAS-проект + физическое устройство.
- **Уведомления при отмене и просрочке заказа не отправляются.** Из шести
  значений `NotificationType` реально используются три (`NEARBY_OFFERS`,
  `PICKUP_REMINDER`, `ORDER_COMPLETED` — `orders.service.ts:185`,
  `notifications-scheduler.service.ts:84,114`). `ORDER_CANCELLED` и
  `ORDER_EXPIRED` определены в enum, но нигде не диспатчатся — проверено
  прямым grep по всему backend. Отмена самим пользователем — не критично (он
  и так знает), но **автоматическая просрочка шедулером — уведомления нет
  вообще**: пользователь может не узнать, что не забрал заказ и деньги
  потрачены впустую, если не откроет приложение сам.
- **Мультиаккаунтность заведения.** Один владелец = один логин, без
  под-аккаунтов персонала (кассир, менеджер) — явный пункт бэклога уже в
  ШАГ 0 ("Мультиаккаунтность — в бэклог"). Для сети из одного человека за
  кассой в бете нормально; для реального заведения с сменами — нет.
- **Онбординг заведений не масштабируется.** Только ручной, через
  `POST /businesses` от ADMIN (форма в панели платформы с ШАГ 11, но всё ещё
  по одному заведению за раз руками). Приемлемо для пилота на несколько
  десятков заведений в Москве, не годится для роста без самостоятельной
  регистрации с модерацией.
- **Карта на native не проверена вживую.** `MapScreen.native.tsx` написан по
  документированному API `react-native-maps`, но в этом окружении разработки
  нет iOS/Android-симулятора — код ни разу не запускался на реальном
  устройстве. То же самое — geo-пермишен в состояниях "выдано" и
  "заблокировано навсегда" (браузерный sandbox всегда возвращает `denied`,
  ветки `granted`/`blocked` не пройдены живьём).

## Функциональный бэклог

- **QR-сканирование камерой для подтверждения выдачи** — сейчас только ручной
  ввод 6-значного pickup-кода в панели бизнеса. Комментарий-заготовка на это
  был ещё в `orders.service.ts` при описании QR-кода в ШАГ 5, но UI так и не
  появился — ручной ввод полностью закрывает сценарий, камера — про скорость
  на кассе при нагрузке.
- **Пагинация `GET /orders` и `GET /offers?businessId=`** — сейчас без
  ограничения сверх стандартного `pageSize` офферов; для беты с умеренным
  объёмом ок, при росте числа заказов на одно заведение станет проблемой.
- **SMS/email как канал уведомлений** — в бете только push (ШАГ 0). Часть
  пользователей может не давать push-разрешение вовсе — тогда они выпадают
  из всех уведомлений полностью, включая критичные (напоминание о самовывозе).
- **`OfferStatus.DRAFT`** определён в схеме и даже подписан в UI админки
  ("Черновик"), но недостижим: `CreateOfferDto` не принимает `status`,
  `OffersService.create()` жёстко ставит `ACTIVE`. Либо достроить
  черновик-флоу (создать → отредактировать → опубликовать), либо убрать
  значение из enum, чтобы не вводить в заблуждение.
- **`BusinessStatus.PENDING`** — тот же паттерн незадействованного значения: онбординг всегда
  создаёт заведение сразу `ACTIVE` (самостоятельная регистрация с модерацией
  вне скоупа). `PlatformStats.businessesPending` в панели платформы будет
  показывать 0 всегда, пока это не меняется — метрика без данных.
- **Количество в заказе всегда 1** (мобильное приложение) — соответствует
  модели "сюрприз-пакет" TGTG-подобных сервисов, но если товар допускает
  бОльшие партии (например, продукты из магазина), степпер понадобится.
- **Live Activity на экране блокировки** (стрелка-компас + метры до выдачи,
  из брифа "2026/27 тренды" — bento-редизайн главного экрана). Технически
  требует нативного iOS-расширения (WidgetKit/ActivityKit) — Expo managed
  workflow такое не поддерживает без eject в bare workflow, который стоит
  части преимуществ managed (OTA-обновления и т.п.) ради одной фичи, доступной
  только на iOS 16.1+. Сознательно не делали в этом заходе — см. обсуждение
  с пользователем при запросе редизайна. Если понадобится: отдельный native
  module (`expo-live-activity` или самописный WidgetKit extension), плюс
  Android-эквивалента у концепции по определению нет (Live Activities —
  iOS-only API).
- **"Умный расчёт времени в пути" / синхронизация с кухней заведения**
  (тот же бриф: "Клиент будет через 7 минут" → кухня начинает упаковывать
  к приходу). Реальная фича, не просто UI — нужен бэкенд-контур: фоновое
  отслеживание геопозиции пользователя после брони заказа (сейчас
  `usersApi.updateLocation` вызывается best-effort при получении
  разрешения, не при активном заказе), ETA-расчёт (расстояние + режим
  передвижения), push/сокет-сигнал в панель бизнеса с "тикающим" таймером
  до прихода. Не строили — UI без реального бэкенд-контура за ним было бы
  ровно тем "half-finished implementation", которого сознательно избегаем
  в этом проекте.

## Технический долг

- **Redis поднят в Docker Compose, но backend его не использует** ни разу —
  ни для кэша, ни для очередей, ни для rate-limiting. Либо начать
  действительно использовать (например, троттлинг гео-дайджеста уже сейчас
  реализован через SQL-запрос к таблице уведомлений — переезд на Redis дал
  бы честный TTL вместо запроса "не было ли уже отправлено за N часов"),
  либо убрать сервис из компоуза, чтобы не платить за то, что не работает.
- **Haversine вместо PostGIS** для гео-поиска — один raw SQL запрос на
  `/offers/nearby`, работает нормально на объёме беты; PostGIS понадобится
  при росте плотности офферов на город (индексы по геометрии вместо полного
  скана с вычислением расстояния на каждой строке).
- **Модель `Payment`** — добавлена сверх исходного списка сущностей ради
  идемпотентности вебхука по `externalId`; при реальном провайдере она уже
  пригодится как persistent audit trail, но если платежи останутся mock
  дольше — кандидат на упрощение (вопрос был явно оставлен открытым в
  README ШАГ 5, ответа так и не последовало).
- **Прод-версия Prisma закреплена на 6.19.3** осознанно (7/8 ломают
  классический `datasource.url`, требуют driver-адаптеров) — нужно будет
  разово мигрировать при апгрейде, не автоматически.

## Известные ограничения окружения разработки (не баги продукта)

- Built-in browser tool этого окружения намеренно подавляет нативные
  `confirm()`/`alert()` диалоги — путь клика "да" в диалогах отмены заказа,
  архивации оффера, блокировки заведения не пройден через UI-клик ни разу;
  везде проверено прямым `curl`-запросом к тому же эндпоинту и визуальным
  подтверждением результата после релоада. Разница между "не проверено" и
  "не работает" здесь принципиальна: сам код диалога идентичен по структуре
  уже проверенным вызовам (`create`/`complete`).
- IPv6-vs-IPv4 класс багов с Docker healthcheck (`wget http://localhost/`
  резолвится в IPv6 первым) — пофикшен конкретно для admin в ШАГ 12; если
  появится новый сервис за nginx/похожим образом, тот же паттерн
  (`127.0.0.1` вместо `localhost`) стоит применить сразу, не ждать, пока
  здоровье контейнера снова будет врать.

## Что нарочно не трогали (решения ШАГ 0, актуальны до реального запуска)

Зафиксировано как дефолт "меняем по запросу", если что-то из этого перестало
подходить бизнесу — пересмотреть перед реальным пилотом, не молча оставлять:

- Возрастные/лицензируемые товары (алкоголь и т.п.) — категории ограничены
  списком `food`/`bakery`/`flowers`/`groceries`, юридическая часть не тронута.
- No-show: `quantityLeft` не возвращается при просрочке (товар считается
  потерянным для заведения) — соответствует бизнес-модели TGTG-подобных
  сервисов, но это продуктовое решение, не техническое ограничение.
- Комиссия — теперь настраиваема по заведению (ШАГ 11), глобальный дефолт
  `PLATFORM_COMMISSION_PERCENT=25` остаётся для новых заведений без
  явной настройки.
